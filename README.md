# Device Monitoring API

A small backend API for ingesting and viewing data from devices in a monitoring system.

Built with **Python**, **Django**, and **Django REST Framework**. Devices periodically report telemetry (temperature, power, voltage), and the system automatically creates alerts when thresholds are exceeded.

---

## Features

- Full CRUD for devices
- Receive and store telemetry data via `POST`
- Retrieve the latest telemetry of a device
- Retrieve telemetry history within a date range (paginated)
- Automatically create an alert when temperature exceeds **70°C**
- Automatically resolve open alerts when temperature drops back below **70°C**
- List and view alerts (read-only)
- Input validation for all fields
- Proper HTTP error responses (`400`, `404`, `405`)
- Cursor-based pagination for list endpoints
- Database index on telemetry `timestamp` for fast range queries

## Architecture

The project is organized into two main parts:

- `config/` → Django project settings and root URL config
- `devices/` → the main app containing:
  - `models.py` → `Device`, `Telemetry`, `Alert`
  - `serializers.py` → validation and (de)serialization
  - `views.py` → API endpoints (ViewSets)
  - `pagination.py` → custom `CursorPagination` classes
  - `urls.py` → route registration
  - `factories.py` → test data factories
  - `tests/` → test suite

## API Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| `GET` | `/api/devices/` | List all devices |
| `POST` | `/api/devices/` | Create a new device |
| `GET` | `/api/devices/{id}/` | Retrieve a device |
| `PATCH` | `/api/devices/{id}/` | Partially update a device |
| `DELETE` | `/api/devices/{id}/` | Delete a device |
| `GET` | `/api/devices/{id}/latest/` | Latest telemetry of a device |
| `GET` | `/api/devices/{id}/telemetry/?from=&to=` | Telemetry history in a date range |
| `POST` | `/api/telemetry/` | Ingest telemetry data |
| `GET` | `/api/alerts/` | List all alerts |

## Setup & Run

### With Docker

1. Copy `.env.example` to `.env` and fill in the values:

   ```bash
   cp .env.example .env
   ```

2. Build and start the containers:

   ```bash
   docker compose up --build
   ```

The API will be available at `http://localhost:8000/`.

### Without Docker

1. Clone the repository:

   ```bash
   git clone https://github.com/Zahra-Dehghan98/Device-Monitoring-API.git
   cd Device-Monitoring-API
   ```

2. Create and activate a virtual environment:

   ```bash
   python -m venv venv
   source venv/Scripts/activate   # Windows
   # or
   source venv/bin/activate       # Linux / macOS
   ```

3. Install dependencies:

   ```bash
   pip install -r requirements.txt
   ```

4. Copy `.env.example` to `.env` and fill in the values:

   ```bash
   cp .env.example .env
   ```

5. Create the PostgreSQL database (name must match `DB_NAME` in `.env`).

6. Run migrations:

   ```bash
   python manage.py migrate
   ```

7. Start the server:

   ```bash
   python manage.py runserver
   ```

The API will be available at `http://localhost:8000/`.

## Design Decisions

### 1. `device_code` as telemetry input

Clients send a human-readable device code (e.g. `"INV-001"`) instead of a numeric foreign key.  
The serializer resolves this code to the corresponding `Device` instance and returns `404` if no matching device exists.

### 2. Alert creation inside the serializer

Alert logic lives in `TelemetrySerializer.create()`, not in the view.  
This keeps the view layer thin, follows the task requirement of not putting business logic in views, and centralizes the rule in one place.

### 3. Automatic alert resolution

- Temperature **above 70°C** → a new alert is created.
- Temperature **at or below 70°C** → all open (unresolved) alerts for that device are marked as resolved.

This mirrors real monitoring systems, where alerts close themselves once the condition clears.

### 4. Cursor-based pagination

Telemetry is time-series data, and new records are constantly being appended.  
Page-number pagination can produce duplicates or skipped records when the dataset shifts between page requests.  
Cursor pagination avoids this by anchoring each page to a stable pointer.

### 5. Database index on `timestamp`

The history endpoint filters telemetry by date range (`?from=&to=`).  
Adding `db_index=True` on `Telemetry.timestamp` speeds up these range queries.

### 6. Read-only alerts

Alerts are always generated by the server, never submitted by clients.  
Therefore, `AlertViewSet` exposes only `list` and `retrieve` — `POST`, `PUT`, `PATCH`, and `DELETE` return `405 Method Not Allowed`.
